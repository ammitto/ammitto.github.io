= Ammitto Website

image:https://img.shields.io/github/license/ammitto/ammitto.github.io.svg[License]

== Introduction

This is the Ammitto sanctions database website, located at https://www.ammitto.org.

It is a https://vuejs.org[Vue.js 3] application built with https://vitejs.dev[Vite] and https://vite-ssg.com[Vite SSG] for static site generation.

== Features

* **Sanctions Search Database** - Search sanctioned entities from the publishing sources
* **Ontology Browser** - Explore the Ammitto knowledge graph schema
* **Lightweight Search** - Client-side FlexSearch over a compact index rather than the whole graph
* **Virtual Search Results** - Measured result rows keep scrolling lists bounded, with a show-all option
* **Class Relationship Graph** - An on-demand ontology graph with keyboard selection, pan and zoom
* **Dark Mode** - Full dark mode support
* **Responsive Design** - Mobile-first design with Tailwind CSS

=== API data in development

`npm run dev` serves `/api/v1/` from `public/api/v1`. That directory holds
whatever `build:api` copied from a data-cn checkout (found beside or inside
this repository, or named by `AMMITTO_DATA_CN_DIR`). Without one it holds
only the small sample committed for CI, and pages that need a file the sample
lacks will not load. The full data is generated at deploy time and published
at https://www.ammitto.org/api/v1/.

Before starting, `npm run dev` checks that `public/api/v1` holds every file
the site requests at a fixed path (the search index, `stats.json`, the
facets, the browse pages' `node/*/index.jsonld` files and so on; the list is
`REQUIRED_STATIC` in `scripts/dev-data-mode.js`) plus each published
`sources/*.jsonld`. The sample lacks most of them,
and so does a data-cn checkout, which covers CN only. When any is missing it
warns and, at a terminal, asks which mode to use:

Live (default):: files missing from `public/api/v1` are fetched from
`www.ammitto.org`. Files present locally are still served locally, so a
local edit overrides the published copy.
Sample:: only `public/api/v1` is served; a missing file answers 404.
Quit:: stop without starting the server.

Set `AMMITTO_DEV_DATA=live` or `AMMITTO_DEV_DATA=sample` to skip the prompt.
In live mode a request the published site leaves unanswered for 15 seconds
gets a 504.
When stdin is not a terminal and the variable is unset, only `public/api/v1` is served,
so scripts never wait for input or reach the network unasked. Live mode
applies to the dev server only; `npm run build` and `npm run preview` never
fetch from the published site.

=== Search and asset performance

Completed search results beyond the first 50 cards use virtual rows. Partial
results retain their progressive presentation. “Show all loaded results”
provides an alternative for reading every loaded link without virtualization.
The ontology graph loads separately from search and uses the schema files,
not the full sanctions graph.

In production, a service worker caches only a bounded allowlist of this build's
hashed static assets. It does not cache API data, HTML, OpenAPI or query
downloads. Updates activate naturally after existing tabs close; the worker
does not force a reload or provide an offline sanctions-data fallback.

The search page itself keeps a separate device cache (Cache API, named
`ammitto-search-assets-v1`) so repeat visits do not download the search data
again. It stores only content-addressed search assets named by the current
`search-runtime/index.json`: the query partitions, ids, filter columns, row
chunks and suggestion list (about 11.9 MB of `.bin` files for the October 2026 corpus),
plus the `api/v1/search-index/*.json` shards (about 22.7 MB), each keyed by its
SHA-256. Freshness is always decided by the network: `index.json` and the
shard manifest are fetched from the server on every visit, and a cached entry
is used only when its hash matches what that fresh `index.json` names. Every
cached read is re-hashed; a mismatch is discarded and refetched. Entries the
current `index.json` no longer references are deleted (pruned per data
generation). It is not an offline fallback: without the network the page
cannot learn which generation is current, so it does not answer from cache.
Storage failures (quota, private browsing, eviction) fall back to the network.

To compare search CPU costs, save a baseline version of
`src/composables/useSearchIndex.ts` and run:

[source,shell]
----
NODE_ENV=production node scripts/measure-search-performance.mjs /tmp/useSearchIndex-before.ts 60000 5
----

This runs five alternating samples per version in separate child processes,
using 60,000 synthetic rows. It reports cold index loading and repeated queries
after one warmup query, with exact result-order checks. Both versions use the
current dependencies and helper modules. Network, JSON parsing, rendering and
production page-load performance are outside this measurement.

=== Manually maintained source freshness

China's source card and entity pages show the latest announcement included in
the published snapshot, separately from its repository commit date. Neither
date establishes when the official websites were last checked or when a
contributor imported a notice; those dates are shown as not recorded.
Newer official announcements may still need manual import.

The deployment generates `/source-freshness.json` from the checked-out
`data-cn` revision and its harmonized announcements. This website provenance
file is separate from the sanctions API catalogue. Local snapshots without
the file show unknown dates rather than reusing the site's build timestamp.

=== API contract and SPARQL

The `/api` page documents the static API and local query examples.
`public/openapi.json` publishes its OpenAPI 3.1 contract at `/openapi.json`;
it stays outside the generated `public/api/v1` directory so harmonization
cannot replace it. Query files are published from `public/queries/`.

See link:docs/api.adoc[the API and SPARQL guide] for slice references, search
shards, tested query predicates, local Turtle queries and using a SPARQL store
you operate. Ammitto currently provides Turtle files rather than a hosted
SPARQL endpoint.

Validate every documented response family and parameter branch against dated,
bounded HTTP-response fixtures with the CI-only Ruby dependencies:

[source,shell]
----
BUNDLE_GEMFILE=.github/validation.Gemfile bundle install
BUNDLE_GEMFILE=.github/validation.Gemfile bundle exec ruby scripts/verify-api-contract.rb
----

The verifier uses JSONSchemer and also rejects missing required fields and wrong
field types. CI runs it separately from the website's Node tests; it does not
add a website runtime dependency. See `tests/fixtures/openapi-responses.json`
for capture URLs and dates. Fixtures are excerpts rather than a complete corpus.

=== Deployment

The site is automatically deployed to GitHub Pages via GitHub Actions.

The deployment workflow:

. Checks out the website repository
. Checks out the ammitto gem repository
. Clones the data-* repositories the workflow names
. Runs `ammitto harmonize` over the explicitly named sources to generate
  API data. They are listed rather than discovered with `--scan`, so that
  the harmonized source set stays exactly the set
  `.github/harmonize-thresholds.json` was calibrated against
. Builds the Vue.js application with Vite
. Deploys to GitHub Pages

To trigger a deployment:

[source,shell]
----
git push origin main
----

Or manually via GitHub Actions workflow dispatch.

=== Rendering large lists

A search can match tens of thousands of entities while the page shows 50 at a
time. Keep the full match list as plain index rows, and build display objects
(cards, formatted fields) only for the rows on screen, in the computed that
slices the page. Cache what was built, so "Load More" builds only the new
rows. The result count, filters and sorting read the rows, never the cards.

The same applies to pure helpers called once per rendered item with a small
set of inputs, such as a badge colour per source: compute each distinct input
once and reuse the result (`pillToneVars` in `src/config/palette.ts`).

`SearchPage.vue` (`filteredEntities` holds rows, `paginatedEntities` builds
cards) is the reference implementation.

== Data Sources

The sources named in `publishing_sources` in
`.github/harmonize-thresholds.json` contribute entities to the site, including
Russia (`ru`). Each publishing source must provide a non-empty aggregate and
meet its entity floor. Supporting vocabularies are checked separately from
entity counts.

Russia's processed announcements are maintained from the official source
snapshots in `data-ru`. Their publication does not establish that every later
announcement has been imported. The threshold manifest distinguishes the
historical full-corpus calibration from this RU publication update.
